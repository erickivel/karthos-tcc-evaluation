# Local qualification for official thesis v2

This is a focused contract qualification, not another local evaluation pilot. Run it against the product source and lock generated by the build-from-commit workflow. Keep every failed attempt in its original directory. Commands refuse an existing output directory; use a new suffix to rerun. Rejected reuse leaves all existing files unchanged. The kind helper writes a final report only when that invocation created the output directory; failures after creation remain recorded there.

## Prerequisites and scope

Install the pinned product's Go/Task toolchain, Docker, kind, kubectl, Helm, istioctl, curl, jq and Python dependencies (including PyYAML). Use the Istio tool version pinned by the evaluation build. The product fixtures build their small application images locally. Images and command logs are recorded separately from GKE evidence; local builds are not substituted for the immutable GKE deployment images.

Use a disposable local workstation/container engine with capacity for the product's two-node kind fixture. The helper refuses an existing `karthos-thesis-*` cluster name and binds every Kubernetes operation to its private kubeconfig/context. Product fixture node selectors are adapted only from `karthos-test-{control-plane,worker}` to the owned nodes; before/after render artifacts are retained. The existing product setup uses the local `karthos-kind-registry` on port 5001 and port 8080 for the fixture; ensure those ports are available or the existing registry belongs to your local testing setup. The shared registry is deliberately retained after cleanup, never removed by this helper.

On Linux, check `sysctl fs.inotify.max_user_instances fs.inotify.max_user_watches` before creating the fixture. If node logs report a failed inotify allocation / “Too many open files”, ask the host administrator to raise the limits temporarily; kind documents `max_user_instances=512` and `max_user_watches=524288` in its [known issues](https://kind.sigs.k8s.io/docs/user/known-issues/#pod-errors-due-to-too-many-open-files). Record the original values and restore them after owned-cluster cleanup. Do not treat this node-boot failure as a Karthos result.

Do not run against a production or shared Kubernetes context. The helper installs/removes its owned Istio, deploys fixtures and Karthos, generates controlled traffic, and replaces a fixture Pod. It does not create GCP resources.

## 1. Capture structure, replacement and arbitration

From the built evaluation `source/` directory:

```sh
python3 -B -m evaluation.gke.local_kind_qualification \
  --product /absolute/build/product \
  --product-lock /absolute/build/published-product-lock.json \
  --out /absolute/new/kind-evidence \
  --cluster-name karthos-thesis-UNIQUE_LOWERCASE_SUFFIX
```

The helper verifies and copies the product into its new evidence directory before invoking scripts; image and Helm work therefore do not mutate the immutable build source. The helper reuses the product's existing deployment scripts and public discovery/deployment CLI. It records:

- Exact product identity and command logs.
- Default capability profile and actual per-business-Pod sidecar readiness/counters.
- An explicitly supplied **business-namespace** mesh profile, with provisional trace availability accepted only after positive actual receiver span observations.
- Generated and mounted source plans, collector configuration and API source provenance.
- Forty parsed actual calls per source (30 normal, 10 intentional errors), stable pre-load counters and observed post-load deltas; other-source increases prevent a single-contribution pass.
- Before mesh validation, run the pinned protocol-client Job, require its measured-traffic completion log, and delete it. This supplies request counters for the protocol-only server that gateway journeys do not call. It is setup traffic outside the later gateway-to-service accounting population.
- Eleven entity kinds/seven directed relationships, same-name/different-UID replacement across nodes and a retained read of the original snapshot.
- Actual removal of owned Istio, fresh public discovery and explicit trace redeployment.
- Cluster node UID identities and owned-cluster cleanup status.

The business-scoped fixture is **not a successful default cluster-wide detector test**. Kind's unmeshed storage provisioner can legitimately make the native detector return partial. The original default profile stays in the evidence. No GKE claim inherits this scoped exception: GKE uses its own live configuration and discovery evidence.

On failure, inspect `kind-report.json` and `commands.json`. Missing accounting, identities or configuration never becomes a pass. If node identities cannot be verified during cleanup, the helper leaves the cluster for explicit inspection rather than deleting an uncertain target. Verify cleanup before another attempt.

## 2. Run controlled semantics and API fixtures

Start a separate empty VictoriaMetrics instance at a loopback-only address. Use the VictoriaMetrics version/digest recorded in the frozen artifact lock (the reviewed product uses 1.138.0); do not connect to an existing results database. For example, using your recorded immutable image:

```sh
docker run --rm -d --name karthos-thesis-local-vm \
  -p 127.0.0.1:18428:8428 VICTORIAMETRICS_IMAGE_AT_SHA256
```

Then run:

```sh
python3 -B -m evaluation.gke.local_qualification \
  --product /absolute/build/product \
  --product-lock /absolute/build/published-product-lock.json \
  --kind-records /absolute/new/kind-evidence \
  --vm-url http://127.0.0.1:18428 \
  --out /absolute/new/local-contract-evidence
```

This runs the actual VictoriaMetrics source-query integration subcases; known duration helper; counter reset/expiry tests; traffic-idle-traffic helper; and the seeded public-API helper plus independent five-question scorer. It compiles the API helper before starting its bounded server lifetime and terminates that child after scoring. It verifies the live-kind product identity and required structure/arbitration/retained records, assembles temporal evidence from actual assertions, then calls the existing receipt scorer.

The output `local-contract.json` includes five checks with referenced files/hashes. Exit 0 requires all five to pass; absent kind evidence or failed helper commands produce an incomplete receipt and exit 2. The command does not create success flags from a build or invent live observations. Remove only the VM instance you created:

```sh
docker stop karthos-thesis-local-vm
```

## 3. Prepare the official run

Pass the generated receipt and its neighboring evidence files to `gke-eval.sh prepare --local-evidence ...`. Preparation verifies exact product revision/source hashes and the referenced artifact checksums. Keep local qualification distinct from GKE outcomes: it does not establish independent-VM host accuracy, cloud timing or production capacity.

The helper implementations have focused regression coverage. A newly ported live-driver path must be exercised and its receipt inspected before claiming fresh live qualification; passing pure fixture tests alone is not that evidence.
